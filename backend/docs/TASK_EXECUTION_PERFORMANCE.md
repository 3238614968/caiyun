# 任务未完成与执行性能修复

## 日志对应的问题

- 校园海报有失败动作时，仍可能输出绿色成功并让整批任务显示成功。
- 领取云朵原先排在后续活动前，后续产生的奖励留在待领取列表。
- “今日已执行”只判断是否有日志，失败或待条件记录也会阻止再次触发批次。
- 批量账号操作按账号串行执行，同账号的活动入口、访问日志被反复初始化。
- 抢兑预热只获取 JWT，设备标识和 HTTP 会话到点后才创建；同步预热还可能挡住整点定时器。

用户提供的日志生成于前一个协议修复制品之前。新版本继续保留 V3 领取、实际到账和兑换结果确认；旧历史日志不会改写。

## 当前行为

| 环节 | 修复与优化 |
| --- | --- |
| 活动会话 | 同一账号客户端、同一 JWT/SSO 与活动复用初始化，缓存 10 分钟；凭据变化重新初始化，初始化失败不缓存 |
| 多账号批量操作 | 使用有上限的账号工作池，受 Worker 的 TASK_CONCURRENCY 限制，去重重复账号；每个账号内部按任务顺序执行 |
| 重复日常批次 | 跳过当天已成功的动作，保留失败/待条件任务；任务中心、领奖盘点、云朵领取、统计和收尾继续刷新 |
| 批次收尾 | 活动先执行，之后领取云朵、更新统计、清理临时资源，避免遗漏后产生的奖励 |
| 校园海报 | 同一步动作只提交一次；失败提供具体原因，不连续重复相同失败上传；仍未完成的服务端状态如实展示 |
| 前置条件 | 本月尚未满足真实自动备份时，翻倍奖励显示 pending；不会伪造备份或学生资格 |
| 批次结果 | 真实子任务失败使批次显示失败，已经成功的动作不因整批自动重试再次上传、抽奖或领取 |
| 抢兑准备 | 所有场次提前 60 秒注册精确定时器并异步预热 JWT、设备和 HTTP/入口连接；每个准备完成的账号立即发布热会话，15 秒补查一次新增任务 |
| 抢兑执行 | 到点重新查询 pending 任务，防止旧快照执行已删除或改期任务；按日期、场次、任务 ID 去重，各任务独立取用有效热会话，不等待全部账号预热 |
| 抢兑状态 | 跨 Worker 由数据库条件更新抢占执行权；未取得执行权、取消等跳过不统计为兑换失败 |

滑块仍在实际兑换前获取和验证，没有提前缓存未知有效期的验证码。上游 AI、上传、滑块服务的处理耗时仍会影响总耗时。

## 抢兑预热时间

| 抢兑场次（UTC+8） | 开始预热 | 触发执行 |
| --- | --- | --- |
| 默认上午场 | 09:59:00 | 10:00:00 |
| 默认下午场 | 15:59:00 | 16:00:00 |
| 自定义 17:51 | 17:50:00 | 17:51:00 |
| 跨日 00:00 | 前一天 23:59:00 | 次日 00:00:00 |

规则时间、任务指定时间、补货时间列表和 Cron 都使用同一预热流程；周期及节假日策略按目标场次日期判断。预热窗口内新增任务会在下一次 15 秒检查补热，已就绪的账号会话复用，凭据更新后重新准备。Worker 在窗口内启动会立即检查，临近整点才创建的任务仍在到点查询中纳入执行。

`EXCHANGE_FIRE_OFFSET` 默认 0，保留 ±5 秒的时钟纠偏范围，兜底触发也遵守该偏移。`开始预热` 日志提供目标时间与剩余毫秒；`开始执行` 提供触发偏差毫秒。这个偏差表示任务派发时刻，滑块与网络耗时仍会使实际兑换请求晚于派发。

2026-10-01 10:00 的用户日志显示，旧版本 09:59:30 才预热，整点精确触发和兜底又重复派发了相同任务。这次分别修复为提前一分钟和每场次去重。上游 `610 / GK` 的具体拒绝条件没有由抓包证明，不能将调度修复等同于会员商品必定兑换成功。

## 验证与使用

```bash
cd backend
go test ./... -timeout 3m
go vet ./...
```

回归覆盖：重复查询仅初始化一次入口、账号/凭据隔离、初始化失败后恢复、限定账号并发和重复账号去重、热会话一次性使用及过期/凭据更新、失败批次不整批重放、任务末尾领取和已完成动作跳过；默认/自定义/跨日场次提前一分钟，窗口内启动补热，20 个并发触发只派发一份任务，新增任务与次日场次继续执行，取消任务不误计失败。

模拟请求验证了同一账号 10 次信息查询只初始化 1 次入口和 6 次初始访问日志；旧流程相应为 10 次入口和 60 次访问日志。这个请求数量对比不等于真实服务端固定的加速倍数。

本次本地验证环境为 Windows/AMD64、Go 1.27.1、CGO_ENABLED=0，Go 测试与 vet 通过；需要 CGO、真实 MySQL/Redis 的测试和 Linux 进程运行未在本机验证。Linux AMD64 制品经交叉编译、ELF 架构和校验和检查，真实抢兑时序及上游结果需部署后确认。

替换 API 与 Worker 的同版本制品并重启，无新增 SQL 迁移。默认继续采用部署配置中的 TASK_CONCURRENCY 和抢兑并发；优先使用默认值，结合数据库、服务器和上游限制评估调整。

再次执行日常批次可继续未完成任务；单独选择某个任务时保留主动重跑能力。会员奖品最终领奖仍按用户要求留待后续。
