# 任务未完成与执行性能修复

## 日志对应的问题

- 校园海报有失败动作时，仍可能输出绿色成功并让整批任务显示成功。
- 领取云朵原先排在后续活动前，后续产生的奖励留在待领取列表。
- “今日已执行”只判断是否有日志，失败或待条件记录也会阻止再次触发批次。
- 批量账号操作按账号串行执行，同账号的活动入口、访问日志被反复初始化。
- 抢兑预热只获取 JWT，设备标识和 HTTP 会话到点后才创建；同步预热还可能挡住整点定时器。

用户提供的日志生成于前一个协议修复制品之前。新版本继续保留 V3 领取、实际到账和兑换结果确认；旧历史日志不会改写。

## 当前行为

| 环节 | 修复与优化 |
| --- | --- |
| 活动会话 | 同一账号客户端、同一 JWT/SSO 与活动复用初始化，缓存 10 分钟；凭据变化重新初始化，初始化失败不缓存 |
| 多账号批量操作 | 使用有上限的账号工作池，受 Worker 的 TASK_CONCURRENCY 限制，去重重复账号；每个账号内部按任务顺序执行 |
| 重复日常批次 | 跳过当天已成功的动作，保留失败/待条件任务；任务中心、领奖盘点、云朵领取、统计和收尾继续刷新 |
| 批次收尾 | 活动先执行，之后领取云朵、更新统计、清理临时资源，避免遗漏后产生的奖励 |
| 校园海报 | 同一步动作只提交一次；失败提供具体原因，不连续重复相同失败上传；仍未完成的服务端状态如实展示 |
| 前置条件 | 本月尚未满足真实自动备份时，翻倍奖励显示 pending；不会伪造备份或学生资格 |
| 批次结果 | 真实子任务失败使批次显示失败，已经成功的动作不因整批自动重试再次上传、抽奖或领取 |
| 抢兑准备 | 先注册精确定时器，再异步预热；提前获取 JWT、设备和 HTTP/入口连接，每个准备完成的账号立即发布热会话 |
| 抢兑执行 | 各任务独立取用有效热会话，不等待所有账号同步预热；不同任务的 Cookie/验证码状态隔离，凭据变化或缓存过期时重新准备 |

滑块仍在实际兑换前获取和验证，没有提前缓存未知有效期的验证码。上游 AI、上传、滑块服务的处理耗时仍会影响总耗时。

## 验证与使用

```bash
cd backend
go test ./... -timeout 3m
go vet ./...
```

回归覆盖：重复查询仅初始化一次入口、账号/凭据隔离、初始化失败后恢复、限定账号并发和重复账号去重、热会话一次性使用及过期/凭据更新、失败批次不整批重放、任务末尾领取和已完成动作跳过。

模拟请求验证了同一账号 10 次信息查询只初始化 1 次入口和 6 次初始访问日志；旧流程相应为 10 次入口和 60 次访问日志。这个请求数量对比不等于真实服务端固定的加速倍数。

替换 API 与 Worker 的同版本制品并重启，无新增 SQL 迁移。默认继续采用部署配置中的 TASK_CONCURRENCY 和抢兑并发；优先使用默认值，结合数据库、服务器和上游限制评估调整。

再次执行日常批次可继续未完成任务；单独选择某个任务时保留主动重跑能力。会员奖品最终领奖仍按用户要求留待后续。
