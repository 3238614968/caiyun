# 抢兑、领奖专区与界面优化记录

核对日期：2026-09-30。参考用户提供的抢兑日志、当前 Go/Vue 实现，以及 `D:/Project/Node/移动云盘SMS` 的滑块与会话实现。

## 抢兑为什么被跳过

日志中的 `17:50:30` 是 `17:51` 时间槽的预热阶段。原查询用实际当前分钟判断任务，导致预热目标被判为不在时间点；已改为按目标分钟及对应日期判断，包括跨日预热。

原 SQL 还会在每个分钟槽加载所有配置了 `restock_times` 的任务，随后把其他时间点的任务记为策略失败并写入数据库。已按目标时间缩小候选查询，其他时间槽的任务不再产生跳过日志或状态写入；实际日历、周期限制仍会报告。

另一个已验证的问题是预定商品保留了单个默认补货时间。用户修改「指定抢兑时间」后，旧默认值仍覆盖新值。现在统一为：

1. 自定义 Cron 优先；
2. 两个或更多时间点为明确的多时段策略；
3. 单个时间点以指定抢兑时间为准，两者同步；
4. 未指定时，回退抢兑规则的时间。

表单会禁用当前不生效的单点输入，提交时只发送一种有效策略；后端的执行、预计触发时间和任务列表显示遵循相同规则。没有读取生产数据库中任务 296/352 的具体字段，不能断言它们各自属于哪个配置冲突，但上述两条代码路径均已修复并有回归测试。

## `610 / GK` 与滑块日志

`/api/sms/solve` 返回 `code=0` 只表示图像识别服务给出了坐标。其日志的 `phone=` 为空，是通用图像识别请求未携带手机号，不等于账号登录失效。

云盘兑换请求 `HTTP 200`、业务 `code=610`、`Error Code：GK` 表示请求到达了活动接口，但兑换没有成功。现有反馈没有给出更具体的服务端原因，不能据此确定为库存、账号资格或滑块失效。

本地已修复的请求问题：

- 移除识别完成后再随机增加或减少坐标的逻辑；直接使用原图坐标，验证坐标在图片范围内。
- 兼容参考识别器的 `x` 与现有服务的 `offset` 返回字段。
- 保留挑战响应的 `x-yun-tid`，兑换使用同一会话中的挑战标识。
- 同一任务的重试复用 HTTP 会话与设备信息，避免重复初始化；凭据接近到期时重新取得授权。
- 失败日志保留识别坐标、置信度、原始业务码与回包。日志详情增加可展开的诊断信息，避免仅显示「活动异常」。

这些改变不能证明真实账号上的 `GK` 已消失。本轮未提交真实兑换请求。

## 领奖专区

新增受保护接口 `GET /api/v1/exchange/prizes?account_id=...`。普通用户只能查询自己的账号；管理员可查询选定的托管账号。权限检查在读取缓存之前执行。

接口分页读取该账号所有奖品记录，按 `flag=1` 筛选全部待领奖品，并按到期时间排序。缺少有效分页数据或超过读取上限时返回错误，不把不完整结果说成「全部」。正常结果缓存 30 秒，同账号并发读取合并为一次请求；`refresh=1` 强制刷新。

界面支持账号切换、搜索、今日到期筛选、本地分页和领取指引。切换账号会取消旧请求，并用请求序号防止旧数据覆盖新账号。领奖区目前展示奖品与指引，短信、实物信息及领取验证按官方流程完成。

## 趋势准确性与卡顿

- 管理员首页原先同时加载个人仪表盘与全局趋势，完成顺序不同会覆盖趋势数据。现在管理员只加载全局统计；趋势由独立、带请求序号的加载流程更新。
- 原历史汇总可能只覆盖部分账号，却与当天所有账号总额相减；缺失日期还被反向填充成相同余额。现在记录采样覆盖数量，缺失或部分覆盖的日期保留断点，不计算虚假涨跌。
- 「今日获得」使用任务日志收益；趋势展示余额净变化，包含兑换支出。新增账号的初始余额不当作任务收益。
- 每日余额采样涵盖全部未删除账号。对每批账号批量读取昨日/上周基线并批量写入，减少逐账号重复查询。
- 实时事件刷新合并，限制并行请求，离开页面后停止排队刷新；抢兑操作完成后自动刷新规则与任务列表。
- 隐藏选项卡延迟挂载，图片映射与初始数据并行加载；移除多层毛玻璃和大面积位移动画，统一卡片、间距和按钮。
- 手机端修正四行统计卡片和底部导航溢出。

历史缺失的完整余额无法从当前总数恢复，界面会如实保留断点，后续采样补齐新日期。

更新需要同时部署新的 API、Worker 和前端构建；只有替换前端无法修复调度器。现有历史任务在新 Worker 中按修正后的时间优先级计算，建议上线后检查对应任务的「时间策略 / 下一次执行时间」。
