# 设备注册 SDK 编码链移植

依据用户提供 HAR entries[1244] 的官方 `fp.min.js`（SDK 3.0.0）及 entries[1302] 的成功设备注册请求，将正常 `encode=5/compress=2` 报文编码接入 Go 客户端。没有引入 Node、浏览器、Python、CGO 或新的 Go 依赖。

## 这次确认的协议差异

官方脚本的 `encode=1/compress=0` 是 `rtype=exception` 异常上报分支。此前用这个格式包裹正常设备数据，不能作为正常 SDK 注册的等价实现。

当前组织使用脚本内的默认配置：内层 `protocol=4`；旧实现写入的 242 并非这份 SDK 的配置。已核实当前 RSA 公钥与 HAR 的 H5 配置一致。

正常流程：

1. 每次生成新的随机 UID，用 RSA PKCS#1 v1.5 加密为 `ep`。
2. 对原始字段按键排序、按 JavaScript 字符串语义生成 MD5 摘要 `tn`。数值先乘 10000，数组、对象、布尔值按原 SDK 的转换规则处理。
3. 按公开配置重命名字段，对指定字段使用 DES-ECB、零填充、base64。保留 SDK 的 UTF-16 `charCodeAt` 语义。
4. JSON 序列化后 gzip，再 base64；以 UID 的 MD5 前 16 个 ASCII 字符作 AES 密钥，IV 为公开协议常量 `0102030405060708`，执行 AES-CBC 零填充，输出十六进制 `data`。
5. 外层发送 `encode=5/compress=2`。只接受业务码 1100 且设备 ID 非空的响应；失败直接返回，不回退异常格式或静态设备标识。
6. 按官方 `SMSdk.getDeviceId()` 规则，无条件在服务端原始 ID 前加 `B`。原始 ID 自身以 B 开头时，最终字符串应为 BB 开头。

抢兑和云朵中心都已接入；活动页 URL 同时用于加密字段和 HTTP Referer，User-Agent 也保持一致。移除了原来额外的 0.5–1.5 秒随机等待。

## 数据采集范围

本次移植的是编码链和当前 HTTP 活动上下文，传入当前 URL、User-Agent、SDK 版本、组织、临时会话标识等已有信息。未模拟随机电量、屏幕、浏览历史、Canvas、音频或插件指纹。

这并不等于在真实浏览器内运行完整 SDK。服务端接受设备注册，仍不证明它会对该设备授予与真实 App 完全相同的活动资格或风险结果。没有复制 HAR 中的旧账号、设备 ID、Cookie 或私钥，也没有重放真实兑换。

## 验证结果

- 从原 SDK 的真实函数生成离线测试向量：DES/AES 密文逐字节一致，覆盖整块、跨块、中文及 emoji；摘要和字段映射与原脚本一致。
- Go 与 pako 的合法压缩流和 JSON 键顺序可能不同，完整报文以解密、解压后的对象一致为准；没有把字节差异错误归因于协议不兼容。
- 生产请求回归检查 `5/2`、活动 URL/Referer、User-Agent、随机密钥不复用、拒绝失败响应、取消，以及 B 前缀边界。
- 使用当前 Go 实现做了一次不带账号 JWT/SSO 的线上注册：通过返回码 1100 检查，取得带前缀共 89 字符的设备 ID，请求耗时约 318 ms。没有领取奖励或提交兑换。
- 本机 Windows amd64 / i5-14600KF，三轮报文生成基准约 0.22–0.48 ms/次（约 1.10 MB 分配/次）。网络耗时另计。

测试向量和来源说明位于 `internal/core/shumei/testdata`；公开字段映射位于 `internal/core/shumei/sdk_config.json`。

后端全量 `go test ./...`、`go vet ./...` 通过；设备前缀边界追加后，设备注册和兑换相关测试再次通过。Linux amd64 二进制已重新生成，版本标记为 `2026.10.07-sdk5-dirty`，位于 `backend/caiyun-linux`，校验文件为 `backend/SHA256SUMS`。当前 Windows 环境未运行需 C 编译器的 race 检查及真实 Redis/MySQL 集成测试。

## 部署与剩余验证

需要重新构建并替换后端二进制，重启 API、Worker，使旧的设备会话失效。前端和数据库结构无需修改。`610/GK` 是否消失仍须看部署后真实兑换结果，不能用设备注册成功替代最终业务验证。
