# 内置滑块识别

抢兑默认使用 Go 后端内置识别器，识别图片不再往返短信服务的 `/api/sms/solve`。获取官方挑战、设备身份及提交兑换仍遵循原有协议；这次改动不改变这些接口的要求。

## 算法与参考来源

参考实现为 `D:/Project/Node/移动云盘短信登录/中国移动云盘/云盘抢兑/sms_login_app/captcha/SliderCaptcha.js`。该实现以灰度大于 30 取滑块区域，对梯度幅值作 NCC 匹配，搜索范围限制在背景中间部分。

内置实现位于 `internal/core/slider/solver.go`，仅使用 Go 标准库，无 Node、Sharp、OpenCV、Python 或 CGO 依赖：

- 一次解码、一次预计算梯度，空间采样限制为最多 1200 点；搜索过程中不反复计算每个像素的梯度模长。
- 结合亮度、带方向梯度、梯度幅值的相关性；匹配前应用相同的 3×3 高斯平滑，减小 JPEG 压缩噪声影响。相关性可容忍缺口的明暗变化。
- 使用透明度遮罩；不透明黑底通过边界连通区域去除，保留滑块内部暗色纹理。腐蚀遮罩后只匹配内部纹理。
- 搜索全部有效水平位置，保留原滑块画布的透明边距，不附加猜测的像素修正。按 `picWidth` 换算服务端坐标；支持完整高度画布，以及带或不带 `puzzleTop` 的裁剪滑块。
- 比较最佳位置与其他位置的峰值差；重复纹理、纹理不足或低置信度不提交兑换，立即刷新挑战，最多三题。失败后不触发外层再次执行这批识别。
- 无共享可变状态，支持多账号并发；尊重请求取消，限制图片大小、像素数和未知垂直位置的搜索范围。

支持 PNG、JPEG、GIF 和 base64 data URI。置信度是相关性分数的映射，不是服务端验证成功概率。

## 配置与日志

```dotenv
CAIYUN_EXCHANGE_SLIDE_SOLVER=builtin
CAIYUN_EXCHANGE_SLIDE_MIN_CONFIDENCE=0.75
```

未设置识别方式时同样默认 `builtin`。显式设置 `remote` 可继续调用原短信服务识别接口，保持旧接口兼容；内置失败不会自动转远端。无效识别方式在提交兑换前报错。Compose 和 Kubernetes 的默认配置已同步。

成功匹配日志增加 `solver=builtin`、`method=内置多特征NCC`、`solve_ms` 和 `peak_margin`，可分别观察本地识别耗时、匹配质量和候选歧义。兑换保留最新挑战的 Cookie 和 `x-yun-tid`。

## 本地验证

在 Windows amd64 / Intel Core i5-14600KF 上，使用参考 Python 项目 `work/slide_probe.json` 中保存的同一张 680×400 背景和 96×400 滑块对照。只读取图片及尺寸，不使用账号凭据。

| 实现 | 偏移 | 匹配置信度 | 图片识别耗时 |
| --- | --- | --- | --- |
| 原 Node `SliderCaptcha.js`，未经修改 | 391 | 0.8226 | 12 次均值 833 ms，中位数 764 ms |
| 内置 Go | 392 | 0.8833 | 三轮基准均值分别为 9.69、9.83、13.93 ms |

Go 基准包含 base64 解码、图片解码、特征计算和匹配，约 11.23 MB、836 次分配/次。Node 对照直接调用原实现并使用现有 Sharp；不计进程启动和网络。单张图的分数与耗时不能推导总体准确率，两种分数也没有概率校准。保存记录和缺口位置为 392；相差一像素是否影响服务端验证未做线上对照。

回归覆盖参考图片、左右边缘、透明边距、黑底、暗纹理、JPEG 质量 50/82/95、半透明滑块、坐标缩放、裁剪滑块、重复纹理拒绝、超大图片、取消和八路并发。模拟抢兑还验证默认不调用远端识别、失败刷新挑战、最新 Cookie/`x-yun-tid` 一致，以及三题失败不提交兑换。

后端 `go test ./...`、`go vet ./...`、`go build ./...` 通过；新增的显式内置、低置信度及无效配置分支也已单独验证。当前环境 `CGO_ENABLED=0` 且没有 C 编译器，未运行 Go race 检查；本轮未运行依赖真实 Redis/MySQL 的集成测试。

## 部署

无需数据库迁移或前端改动。重新构建后端并重启 API、Worker，使内置识别代码生效。使用远端模式的旧部署需检查环境变量并改为 `builtin`。短信登录和设备身份服务仍按原配置保留。
